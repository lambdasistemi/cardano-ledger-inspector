# Implementation Plan: Decode registered Plutus data in tx.intent

## Context

The WASI wrapper already decodes the Conway transaction once to enrich
`tx.intent`, and it already links the pinned `tx-rdf-core` package.
`Cardano.Tx.Blueprint` in that pin provides a pure CIP-57 parser, definition
resolver, and decoder for constructor, map, list, integer, byte-string, and
opaque data forms. The implementation should reuse that engine primitive and
add the missing registry identity/deployment layer rather than duplicate
Plutus semantics in a host.

The reactor cannot rely on a runtime filesystem in the browser. `flake.nix`
will therefore generate a Haskell module from
`docs/inspector/protocols/registry.json` and every manifest-referenced lookup
file during the source-assembly derivation. Adding a manifest entry and its
JSON file changes the generated module at rebuild time without a Haskell edit.
Missing manifest files fail the build.

## Wire Shape

Known output rows gain:

```json
{
  "decoded_datum": {
    "protocol": "sundaeswap-v3",
    "version": "0.0.0",
    "validator": "order.spend",
    "label": "SundaeSwap V3 order",
    "parameterized": false,
    "parameters_known": true,
    "constructor": "Order",
    "fields": {}
  }
}
```

Known script rows use the same annotation envelope under
`decoded_redeemer`. Scalar and collection field values are lossless tagged
nodes: constructor/name/fields, map/entries, list/items, integer/value, and
bytes/hex. A deployment-enriched annotation additionally carries
`deployment` with registry id, scope, owner, address, script role,
`deployed_at`, and stable `reference_input_matches`.

One vertical slice covers behavior, hermetic RED/GREEN proof, and public

Implementation shape:

1. Extend the existing `tx-intent-smoke` first. Use the committed issue #31
   transaction and producer transaction, assert the two labels, ten decoded
   outputs, all four deployment outref matches, the spending
   `decoded_redeemer`, fallback behavior, both parameterization cases, and a
   repeat-run byte comparison. Observe RED for missing annotations.
2. Generate the embedded registry module in the existing WASI source assembly
   from the manifest and its declared blueprint/deployment paths. Do not add
   runtime filesystem IO or a host-side decoder.
3. Parse registry identities and deployment metadata once from embedded bytes.
   Reuse `Cardano.Tx.Blueprint` for CIP-57 schema parsing/resolution and add a
   pure adapter for the registry scaffold's named schema vocabulary.
4. Enrich only successful `tx.intent` output rows and resolvable script rows.
   Match direct validators before instances; enrich from the Amaru journal;
   preserve raw fields and silently fall back on unknown or non-conforming
   values.
5. Document the recursive decoded annotation in the result schema, API
   narrative, OpenAPI generator example, and committed generated OpenAPI JSON.
   Finalize the registry's draft schema note without redesigning its existing
   validators/instances/deployment-registry interface.

## Authorized Build-boundary Exception

`A-001-engine-boundary` authorizes implementation in the local WASI wrapper,
following issue #160 precedent. The blocked cardano-swiss-knife CLI/Node/WebUI
paths consume this artifact. Current native and Extism builds link the pinned
external kernel instead, so their `tx.intent` responses will not be
byte-identical for these new annotations. Re-architecting every target to link
the local wrapper is outside #35; a separate parity issue must be filed and
linked from this pull request before #35 is declared complete.
