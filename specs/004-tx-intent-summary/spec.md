# Feature Specification: Transaction Intent Summary

**Feature Branch**: `feat/add-signer-focused-transaction-intent-summary-to-i`
**Created**: 2026-05-01
**Status**: Draft
**Input**: GitHub issue #28: "Add signer-focused transaction intent summary to inspector"

## User Scenarios & Testing

### User Story 1 - Understand Signing Intent (Priority: P1)

A signer pastes Conway transaction CBOR into the browser inspector and sees a
first-screen summary of what the transaction appears to do before reading raw
decoded fields.

**Why this priority**: Existing decoded JSON is technically correct but does
not answer the signing question quickly enough.

**Independent Test**: Paste the committed SundaeSwap/USDM transaction fixture
and verify the first viewport exposes the self-declared swap label, vendor
justification, missing signers, redeemer count, withdrawal count, and mint/burn
status.

**Acceptance Scenarios**:

1. **Given** pasted transaction CBOR with CIP-style metadata, **When** decoding
   succeeds, **Then** the inspector shows a signer summary before the raw JSON
   browser.
2. **Given** transaction metadata describing a purpose, **When** the summary is
   shown, **Then** it labels the metadata as self-declared rather than verified
   fact.
3. **Given** a transaction with required signer hashes but no witnesses, **When**
   the summary is shown, **Then** missing required signers are visible without
   opening the witness plan.

### User Story 2 - Preserve Ledger Authority (Priority: P2)

The summary is generated by the Haskell/WASI ledger operation from decoded
ledger values and explicit context; the browser only renders the returned view.

**Why this priority**: The project constitution requires ledger semantics to
come from the Haskell ledger layer.

**Independent Test**: Request `tx.intent` through the same ledger operation
boundary as `tx.inspect` and verify the returned JSON contains display-ready
metrics, claims, sections, warnings, and structured fields.

**Acceptance Scenarios**:

1. **Given** the same transaction bytes and explicit context, **When** `tx.intent`
   is run repeatedly, **Then** the result is deterministic.
2. **Given** producer transaction CBOR context, **When** `tx.intent` runs, **Then**
   input context coverage is reported from decoded producer transactions.

## Edge Cases

- Auxiliary metadata may be nested under integer keys; text fields must be found
  without hard-coding one metadata standard layout.
- Transactions may have no metadata, no required signers, no redeemers, or no
  provider context.
- The first viewport is runner-size dependent, so tests must pin or explicitly
  assert viewport geometry.

## Requirements

### Functional Requirements

- **FR-001**: The system MUST expose a `tx.intent` ledger operation.
- **FR-002**: The intent result MUST include display-ready metrics, metadata
  claims, effect rows, warnings, and structured fields for API consumers.
- **FR-003**: The result MUST distinguish self-declared metadata from verified
  ledger facts.
- **FR-004**: The browser MUST render the intent summary before decoded JSON and
  lower-level witness/validation panels.
- **FR-005**: The Playwright regression MUST assert first-viewport placement
  using explicit viewport geometry, not only selector visibility.

### Key Entities

- **Intent Summary**: Haskell-produced JSON answering the signer-focused
  inspection question for one transaction CBOR.
- **Metadata Claim**: A self-declared human statement extracted from auxiliary
  metadata.
- **Critical Effect**: A visible transaction effect such as fee, outputs,
  withdrawals, mint/burn, collateral, scripts, or required signatures.

## Success Criteria

### Measurable Outcomes

- **SC-001**: The SundaeSwap/USDM fixture shows the swap label and Antithesis
  justification in the first viewport at 1280x720.
- **SC-002**: The same viewport shows missing required signers, redeemer count,
  withdrawal count, and no mint/burn status.
- **SC-003**: Existing identity, witness-plan, validation, and browser tests
  continue to pass.

## Assumptions

- This feature is informational and does not sign, submit, balance, patch, or
  validate the transaction.
- Wallet-owned change cannot be inferred from transaction CBOR alone, so the
  summary avoids claiming a net wallet spend.
